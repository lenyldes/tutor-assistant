# Проверка материалов тьютора

Сервис проверяет, собран ли комплект материалов для дневной или недельной записи тьютора. \
Принимает файлы через REST API, определяет категории по именам, сообщает о пропущенных файлах и сохраняет результат проверки в PostgreSQL. \
На главной странице есть готовые сценарии, ручная загрузка и история — проверяющему не нужно вручную составлять запросы или готовить свои файлы.

> 🚀 **AI-Assisted Engineering — совместная разработка с ИИ:** \
> **14 задач OpenSpec** покрывают путь от контракта API до развёртывания и документации; \
> **11 контрольных случаев** описывают полный комплект, ошибки и граничные условия; \
> **3 REST-эндпоинта** доступны через Swagger, curl и страницу с четырьмя готовыми сценариями; \
> единая команда Zero-Defect проверяет код, миграции и тесты в изолированном Docker Compose-проекте.

- Демо: [https://tutor-assistant.lenyldes.ru/](https://tutor-assistant.lenyldes.ru/)
- Swagger UI: [https://tutor-assistant.lenyldes.ru/docs](https://tutor-assistant.lenyldes.ru/docs)

> [!CAUTION]
> **Демо публичное — не загружайте персональные данные детей.** \
> Все готовые образцы вымышленные; \
> API сохраняет имена файлов, размеры и результаты проверок; \
> История доступна всем посетителям стенда.

Для развёртывания используется [production Compose override](docker-compose.prod.yml) с внешней сетью `caddy-public`; \
адрес и TLS настраиваются на обратном прокси сервера.

### Возможности веб-интерфейса

1. Откройте [демонстрационный стенд](https://tutor-assistant.lenyldes.ru/) и нажмите **«Полный daily»** — ответ будет `complete`, без замечаний.
2. Запустите **«Неполный комплект»** — ответ будет `incomplete`, с ошибкой об отсутствующей обратной связи родителя.
3. Запустите **«Нераспознанное имя»** — комплект останется полным, но появится предупреждение. В блоке **«Обращение к API»** видны метод, путь, имена файлов, HTTP-код и фактический JSON.
4. Откройте **«Историю проверок»** и выберите запись — детали читаются из PostgreSQL без повторной загрузки файлов.

Все готовые файлы синтетические. Дополнительные граничные и ошибочные случаи описаны в [каталоге образцов](demo_files/README.md).

## 2. Соответствие техническому заданию

| Возможность | Где проверить |
| --- | --- |
| Проверка `daily` и `weekly`, комплектность и замечания | `POST /api/checks`, главная страница |
| История со статусом и числом всех загруженных файлов | `GET /api/checks` |
| Сохранённый полный результат по ID | `GET /api/checks/{id}` |
| Ошибки пустого набора, неверного типа и неизвестного ID | HTTP 400, 422 и 404 |
| Четыре готовых сценария и ручная загрузка | Главная страница |

Для `daily` обязательны **дневник наблюдений**, **отчёт о занятии** и **обратная связь родителя**. Для `weekly` дополнительно нужно **заключение специалиста**. Категория определяется по имени файла с учётом пробелов, `_` и `-`, без зависимости от регистра. Допустимые расширения: PDF, DOCX, XLSX, JPG, PNG; файл должен быть непустым и не больше 20 МиБ. Непригодный файл остаётся в списке материалов, но не закрывает обязательную категорию. Ошибки отсутствия обязательных категорий дают `incomplete`; одни предупреждения сохраняют `complete`.

Сервис **не извлекает текст из документов и не анализирует их содержимое** — поле `extracted` всегда `{}`. Байты загруженных файлов не сохраняются; в базе остаются результат, имена, размеры и определённые категории. Это осознанный объём тестового задания, а не распознавание документов.

## 3. Архитектура решения

```text
Браузер / Swagger / curl
          │ multipart/form-data и JSON
          ▼
FastAPI (app/main.py, app/api/checks.py)
          ├── Pydantic (app/schemas.py) — контракт и валидация
          ├── checker.py — чистые правила проверки метаданных
          └── SQLAlchemy (app/models.py, app/db.py)
                         │
                         ▼
                 PostgreSQL: checks, check_documents
```

`POST` сначала сохраняет `check_in_progress`, затем синхронно читает файлы, проверяет их имена и размеры и фиксирует итог `complete` или `incomplete`. Поэтому параллельный запрос может увидеть промежуточный статус. `GET` берёт результаты из базы — исходные файлы для него не нужны. Изменения схемы оформлены миграцией Alembic. Статическая страница и API работают на одном адресе, без отдельного фронтенд-сервера.

## 5. Быстрый старт (локальный запуск)

Нужны Docker и Docker Compose. Из корня репозитория:

```bash
docker compose up --build
```

Compose сам подставляет демонстрационные значения из `docker-compose.yml` — копировать `.env.example` для локального запуска не нужно. Контейнер приложения дожидается готовности PostgreSQL, применяет `alembic upgrade head` и запускает API. Данные базы сохраняются в томе `postgres_data`.

- Страница: [http://localhost:8000](http://localhost:8000)
- Swagger UI: [http://localhost:8000/docs](http://localhost:8000/docs)
- Схема OpenAPI: [http://localhost:8000/openapi.json](http://localhost:8000/openapi.json)

**Полное описание всех эндпоинтов и проверка через curl или Postman:** [doc/API.md](doc/API.md).

Пример того же запроса без браузера:

```bash
curl --fail-with-body -sS -X POST http://localhost:8000/api/checks \
  -F record_type=daily \
  -F 'files=@demo_files/дневник_наблюдений.xlsx' \
  -F 'files=@demo_files/отчёт_о_занятии.pdf' \
  -F 'files=@demo_files/обратная_связь_родителя.docx'
```

В ответе будут `check_id`, `status: "complete"`, `issues: []`, сведения о трёх файлах и `extracted: {}`. Затем `GET /api/checks` покажет запись в истории, а `GET /api/checks/{check_id}` вернёт сохранённые детали. Дополнительные команды и работа с Python на хосте — в [локальной инструкции](doc/LOCAL_DEV.md).

### Развёртывание на сервере

На сервере с Docker Compose и заранее созданной сетью `caddy-public` задайте собственные реквизиты БД в `.env` (включая согласованный `DATABASE_URL`), затем запустите:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Этот override добавляет перезапуск контейнеров и подключение приложения к сети прокси. Он не настраивает сам Caddy, домен или TLS и не закрывает порты, опубликованные базовым Compose. Эти параметры настраиваются на сервере отдельно.

## 6. Переменные окружения (.env.example)

Все параметры из [`.env.example`](.env.example) необязательны при запуске через Compose. Чтобы изменить значения, создайте `.env`; учитывайте, что адрес `db` работает внутри сети Compose.

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `APP_ENV` | `development` | Окружение приложения |
| `PORT` | `8000` | Порт приложения на хосте; внутри контейнера всегда `8000` |
| `POSTGRES_USER` | `tutor` | Пользователь PostgreSQL |
| `POSTGRES_PASSWORD` | `tutor` | Пароль PostgreSQL; для публикации нужен свой секрет |
| `POSTGRES_DB` | `tutor` | Имя базы данных |
| `POSTGRES_PORT` | `5432` | Порт PostgreSQL на хосте; `0` — случайный свободный порт |
| `DATABASE_URL` | `postgresql+psycopg://tutor:tutor@db:5432/tutor` | Подключение приложения к БД внутри Compose |

Если меняете пользователя, пароль или базу — согласованно измените `DATABASE_URL`. Уже созданный том PostgreSQL не переинициализируется при смене этих переменных. Значения в `.env.example` предназначены для локального демо; серверный `.env` не нужно добавлять в Git.

## 7. Тестирование и Zero-Defect

```bash
bash scripts/check.sh
```

Скрипт собирает образ, запускает Ruff и проверку лимита файлов, поднимает отдельную тестовую PostgreSQL, применяет миграции и выполняет `pytest -q`. Удаляет только свой временный Compose-проект с томом и не трогает данные обычного стенда. При успехе выводится одна строка. Контрольные входы и ожидаемые статусы — в [OpenSpec](openspec/changes/tutor-assistant-demo/control-cases.md) и [образцах файлов](demo_files/README.md).

## 8. Мотивация участия в проекте

### Почему мне интересен этот проект:
Это возможность сделать продукт, который несёт реальную социальную пользу. Работа над проектом закрывает сразу несколько моих приоритетов обучения:
- опыт работы над реальным проектом в реальной команде;
- разработка промышленного REST API с транзакционными гарантиями, ролевой моделью и интеграцией LLM-моделей;
- успешное закрытие стажировки.

### Как я вижу свою роль в команде:
В первую очередь — **backend-разработчик**, отвечающий за стабильность API, надёжность хранения данных и безопасность. На начальном этапе готов закрывать и смежные задачи: интеграцию фронтенда, скрипты тестовых данных, обсуждение архитектуры.

### Сколько времени готов уделять проекту:
Рассматриваю участие в проекте как полноценную стажировку и готов уделять **~40 часов в неделю (полный рабочий день)** на протяжении **2–3 месяцев**.
