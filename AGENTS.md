# Правила совместной работы и стандарты разработки (AGENTS.md)

Документ определяет обязательные правила, стандарты качества и порядок взаимодействия для ИИ-агентов и разработчиков в проекте.

---

## 1. Общие принципы и язык

1. **Русский язык**: Всё общение в чате, рассуждения, проектная документация, комментарии и описания коммитов ведутся на русском языке.
2. **Итеративность**: Работа ведётся небольшими проверяемыми шагами. Запрещено накапливать крупные нетестированные изменения.
3. **Архитектурное согласование**: Любые архитектурные предложения, спорные моменты и интерпретации требований сначала обсуждаются с пользователем и только после подтверждения реализуются в коде.
4. **Принцип экономии токенов**: Избегать избыточной бюрократии, длинных монологов и генерации промежуточных служебных файлов, если решение уже согласовано в диалоге.
5. **Переносимость**: Использовать доступные инструменты агента; правила проекта не зависят от названий конкретных инструментов редактирования.
6. **Хирургическая точечность изменений**: Для редактирования существующих файлов использовать компактные точечные правки вместо полной перезаписи без необходимости.
7. **Переносимость**: Использовать доступные инструменты агента; правила проекта не зависят от названий конкретных инструментов редактирования.
8. **Хирургическая точечность изменений**: Для редактирования существующих файлов использовать компактные точечные правки вместо полной перезаписи без необходимости.
9. **Тихий вывод команд (Quiet by default)**: Команды тестов и линтеров должны запускаться с флагами тишины (например, `pytest -q`, `ruff check .` и тому подобное). При успехе — минимум вывода, при сбое — только ошибки.
10. **Доступ к Docker из песочницы**: Команду для работы с Docker и Docker Compose сразу запускать через предусмотренное инструментом повышение прав для доступа к Docker API. Не делать предварительный запуск в песочнице: он стабильно завершается `permission denied` на Docker-сокете.
11. **Однократность проверок перед ревью**: Все обязательные проверки выполняются общей командой `bash scripts/check.sh` в финальном блоке перед ревью. Новые обязательные проверки добавляются в этот сценарий; отдельные проверки не запускаются циклически после каждой правки.

## 2. Ограничение объёма файлов (<= 10 000 символов)

1. **Область проверки**: Проверке на объём подлежат создаваемые и поддерживаемые в проекте исходники и документация с расширениями `*.py` и `*.md`, а также файлы `*.js`, `*.css`, `*.html` из каталога `web/`, включая новые файлы до коммита. Сторонние зависимости, виртуальные окружения, кэши, результаты сборки и служебные файлы инструментов агента не проверяются. Авторство по Git не используется: ранее написанные файлы проекта также остаются под контролем.
2. **Лимит символов**: Ни один целевой файл не должен превышать **10 000 символов** (включая пробелы и переносы строк в UTF-8).
   - Лимит защищает контекстное окно модели от перегрузки и предотвращает появление монолитных файлов.
   - 10 000 символов эквивалентны ~300–400 строкам кода при стандартной плотности.
3. **Декомпозиция вместо «утрамбовывания» (искусственного сжатия и минификации)**:
   - Превышение лимита **не означает, что код нужно «утрамбовывать» или сжимать**: категорически запрещено ухудшать читаемость, удалять комментарии, документацию, докстринги, аннотации типов, сокращать имена переменных или выбрасывать логику, проверки и функциональность ради укладывания в лимит.
   - Единственно правильный подход — **провести рефакторинг и декомпозицию**: логически вынести часть кода в отдельный файл (новый модуль, сервис, репозиторий, схему, хелпер), сохранив суть, полноту и корректность решения без потери функционала.
   - **Запрет промежуточных пересчётов**: агенту запрещено тратить токены на постоянные замеры и «упреждающие» подсчёты символов в процессе написания кода. Проверка лимита выполняется строго один раз в конце работы командой `bash scripts/check.sh`. При выявлении превышения файл декомпозируется, а не подгоняется под размер.
4. **Исключения**: Сводная генеральная дорожная карта `doc/ROADMAP.md` и исходные файлы требований заказчика в `doc/SOW.md` являются допустимыми исключениями из лимита.
5. **Автопроверка**: Контроль выполняется однократно в конце работы командой `bash scripts/check.sh`. Промежуточные запуски проверки лимита и ручные замеры символов после каждой отдельной правки запрещены.

## 3. Git-процесс и протокол остановки на ревью (Stop-and-Review)

### 3.1. Ветвление
- Каждое изменение изолируется в отдельной ветке:
  ```bash
  git checkout -b change/<name>
  ```
- Ветка `main` содержит только проверенный и завершённый код.

### 3.2. Формат коммитов
Сообщения коммитов формируются строго по схеме:
```text
<TYPE>: <краткое описание изменений на русском языке>
```

**Разрешённые типы (на английском языке)**:
- `ADD:` — добавление новой функциональности, модулей, тестов или документации.
- `UPD:` — обновление существующей логики, настроек, рефакторинг без смены назначения.
- `FIX:` — исправление ошибок, багов, опечаток.
- `RM:` — удаление неиспользуемого кода, файлов или зависимостей.
- `DOC:` — обновление или добавление документации без изменения кода.
- `TEST:` — добавление или модификация тестов.
- `REFACTOR:` — изменение структуры кода без изменения его поведения.
- `MERGE:` — слияние завершённого изменения в основную ветку.

*Правило анти-тавтологии*: Не дублировать глагол типа в описании (не `ADD: Добавить модуль`, а `ADD: модуль конфигурации приложения`).

### 3.3. Обязательная остановка перед коммитом (Stop-and-Review)
Агенту **категорически запрещено** выполнять `git commit` автоматически.

Перед каждым коммитом агент обязан:
1. Выполнить проверку Zero-Defect командой `bash scripts/check.sh` в тихом режиме (без вывода в чат при успехе).
2. Сформулировать и вывести пользователю **краткую сводку ревью** (без списков файлов, дублирования задач и логов):
   - **Суть изменений**: буквально 1–3 предложения простыми словами о том, что было сделано.
   - **Предлагаемый текст коммита**: строго по формату раздела 3.2.
   - **Ручные проверки**: указывать только при реальной необходимости (шаги ручной проверки, оценка UI, спорные вопросы). Если ручная проверка не требуется, пункт опускается.
3. **Остановиться** и дождаться явного подтверждения пользователя («коммить», «ок» или замечания).

### 3.4. Слияние и завершение изменения
После выполнения всех задач текущего этапа  и подтверждения слияния пользователем выполняются команды ниже. Подтверждение финального коммита и слияния можно получить одним явным ответом на сводку ревью. 

```bash
git checkout main
git merge --no-ff change/<name> -m "MERGE: <краткое описание изменения>"
git branch -d change/<name>
```

## 4. Протокол проверки Zero-Defect

Обязательные проверки запускаются из корня проекта одной командой:

```bash
bash scripts/check.sh
```

Сценарий использует отдельный Compose-проект и удаляет только его контейнеры и тома. В контейнере выполняются Ruff, проверка лимита символов и pytest; на тестовой PostgreSQL применяются миграции Alembic. Локальное виртуальное окружение для обязательного цикла не требуется. При успехе команда выводит одну строку, при сбое — название проверки и короткую диагностику. После исправления ошибки запускается весь сценарий повторно. По мере появления API и UI сквозные сценарии запуска, сохранения истории и отказов добавляются в эту же команду.
