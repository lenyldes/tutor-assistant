# Design

## Context

В репозитории пока нет приложения, моделей, тестов и существующих спецификаций; есть `doc/SOW.md`, OpenSpec и правила `AGENTS.md`. ТЗ задаёт FastAPI, PostgreSQL, SQLAlchemy, Alembic и Python 3.11. Подтверждённые правила находятся в `specs/checks-api/spec.md`, `specs/material-validation/spec.md` и `specs/demo-ui/spec.md`.

## Goals / Non-Goals

**Goals:**
- Разделить HTTP-контракт, алгоритм проверки и хранение так, чтобы правила можно было тестировать без БД, а API — с БД.
- Сохранить видимым промежуточный статус до обработки файлов.
- Обеспечить одинаковый контракт для Swagger, curl и страницы.

**Non-Goals:**
- Парсинг содержимого документов, фоновые задания, авторизация, роли и AI-анализ.
- Постоянное хранение байтов файлов или загрузка файлов со стороннего URL.

## Decisions

### Слои и файлы

Один сервис FastAPI. Конкретный набор файлов для реализации:

| Файл | Назначение |
| --- | --- |
| `app/main.py` | FastAPI, подключение API-роутера и статической страницы `/` |
| `app/api/checks.py` | `POST /api/checks`, `GET /api/checks`, `GET /api/checks/{id}`, преобразование ошибок в HTTP-статусы |
| `app/schemas.py` | Pydantic-модели входа и ответа, перечисления типов, статусов и категорий |
| `app/checker.py` | чистые функции распознавания, проверки файла и сборки итогового результата |
| `app/models.py` | SQLAlchemy-модели `checks` и `check_documents` |
| `app/db.py` | engine, session factory и зависимость сессии |
| `app/config.py` | настройки из окружения, включая URL БД |
| `alembic.ini`, `alembic/env.py`, `alembic/versions/<revision>.py` | конфигурация и начальная миграция обеих таблиц |
| `web/index.html`, `web/style.css`, `web/app.js` | страница, оформление и вызовы REST API |
| `demo_files/*` | небольшие синтетические файлы пяти разрешённых форматов и одного ошибочного расширения |
| `tests/test_checker.py`, `tests/test_api.py`, `tests/conftest.py` | проверки правил и API с тестовой PostgreSQL |
| `requirements.txt`, `Dockerfile`, `docker-compose.yml`, `.env.example` | зависимости, образ, БД и пример окружения |
| `doc/LOCAL_DEV.md` | ранняя техническая инструкция до стабилизации клиентского README |
| `README.md` | окончательная инструкция для проверяющего и HR |

Существующие файлы реализации не изменяются, поскольку их нет. В `.gitignore` добавить только записи для локальных служебных файлов, если выбранные инструменты создают их и текущих правил недостаточно. Каждый поддерживаемый `.py`/`.md` и каждый `.js`/`.css`/`.html` в `web/` должен укладываться в 10 000 символов без искусственного сжатия.

### Поток создания проверки

1. FastAPI валидирует `record_type` через Pydantic (`daily`/`weekly`), проверяет наличие хотя бы одного файла; отсутствие файлов даёт 400, неверный тип — 422 до вставки в БД.
2. API создаёт `checks` с UUID, типом, временем создания, `check_in_progress`, пустыми `issues` и `extracted`; коммитит, чтобы параллельный GET видел состояние.
3. Каждый файл читается в пределах одного запроса. Для него фиксируются исходное имя, фактический размер и размер в КБ. Сначала проверяется расширение, затем размер. При недопустимом расширении или размере больше 20 × 1024 × 1024 байт замечание `warning` сохраняется, распознавание пропускается, `detected_type` пуст. Содержимое файла дальше не используется. Для пригодного файла определяется тип по имени; неизвестное имя даёт `warning`.
4. После обхода файлов множество распознанных пригодных категорий сравнивается с обязательным для типа записи. Для каждой нехватки создаётся `error`; наличие хотя бы одного `error` означает `incomplete`. Порядок замечаний стабилен: замечания по файлам в порядке загрузки, затем ошибки отсутствующих категорий в порядке дневник, отчёт, обратная связь, заключение.
5. В одной транзакции записываются метаданные всех файлов, `issues` в JSONB, окончательный статус, `status_label`, `reason`, `checked_at`; байты файлов не сохраняются. Ответ POST строится из сохранённых данных. `GET` читает их из БД, без повторной проверки.

Схема из двух таблиц подтверждена пользователем: `checks` хранит тип, статус, время, итоговые поля, JSONB `issues` и `extracted`; `check_documents` хранит внешний ключ, порядковый номер файла, имя, тип или NULL, размер в байтах. `GET /api/checks` сортирует по времени создания и `id` по убыванию для стабильного списка, число материалов считает по связанным записям. Для `check_in_progress` список показывает уже созданную запись с нулём сохранённых материалов; детали возвращают состояние с пустыми `issues`/`documents` и пустым `extracted` до завершения. После завершения сохранённые сведения читаются без доступа к исходным файлам.

Альтернатива одной JSONB-таблицы упростила бы миграцию, но затруднила бы независимый подсчёт и выборку метаданных. Отдельная таблица замечаний добавила бы связи и миграцию без пользы для требуемых операций. Чистый `checker.py` отделён от HTTP и SQL, чтобы минимум пять проверок правил были быстрыми и детерминированными.

### Контракт и представление

`POST` и детальный `GET` используют одну модель полного результата: `check_id`, `record_type`, `status`, `status_label`, `reason`, `issues`, `documents`, `extracted`, `checked_at`. В списке: `id`, `created_at`, `record_type`, `status`, `materials_count`. Поле `detected_type` для непригодных и неизвестных файлов сериализуется как `null`; `size_kb` вычисляется из байтов с округлением до ближайшего целого вверх. `reason` для `complete` — пустая строка; для `incomplete` — краткое перечисление отсутствующих обязательных категорий. Эти поля и соответствие хранимых значений JSON закрепляются тестами API. Сообщения для пользователей — на русском.

### UI и демонстрационные файлы

`web/app.js` обращается к относительным URL того же сервиса. Кнопки сценариев загружают локальные синтетические файлы из `demo_files/` как `File` и отправляют тот же `multipart/form-data`, что ручная форма. Полный `daily`: три обязательные категории; полный `weekly`: те же три и заключение; неполный: дневник и отчёт; неизвестное имя: полный `daily` плюс `scan_0041.jpg`. Страница показывает фактический HTTP-код и JSON, а описание отправки формирует из метода, URL, типа и имён файлов. Сырые части multipart не отображает. Точный набор контрольных входов и результатов см. в [control-cases.md](control-cases.md).

### Запуск и проверки

`requirements.txt` фиксирует совместимые версии FastAPI, SQLAlchemy, Alembic, PostgreSQL-драйвера, Pydantic Settings, pytest и HTTP-клиента. `docker-compose.yml` поднимает PostgreSQL и приложение; перед запуском API контейнер выполняет `alembic upgrade head`, БД имеет healthcheck. Конфигурация берётся из `.env`; `.env.example` содержит несекретные демонстрационные значения. API-тесты используют отдельную тестовую БД и миграции, а не подменяют PostgreSQL SQLite. Ранние локальные команды фиксируются в `doc/LOCAL_DEV.md`; клиентский README пишется после стабилизации контракта.

## Risks / Trade-offs

- **[Сбой после записи `check_in_progress`]** → запись может остаться промежуточной; при неожиданной ошибке API фиксирует ошибку в журнале и завершает запрос HTTP 500. Это ограничение синхронной демонстрации, не имитация успешной проверки.
- **[Большой multipart расходует память/диск временного хранения]** → читать поток частями при подсчёте размера, освобождать временные ресурсы; более 20 МБ предупреждать и не засчитывать. Общий лимит транспортного запроса остаётся настройкой сервера при развёртывании.
- **[Публичное демо получает реальные данные]** → заметное предупреждение в UI, только вымышленные файлы в репозитории, отсутствие сохранения содержимого.
- **[У пользователя нет доступа к личному серверу в среде реализации]** → деплой выполняется после предоставления адреса/доступа; до этого проверяется локальный `docker compose up` и готовится конкретная инструкция в README. Секреты не добавляются в репозиторий.

## Migration Plan

1. Выполнить начальную миграцию Alembic на пустой PostgreSQL через Docker Compose и проверить старт API.
2. После автоматических и ручных сценариев перенести compose-конфигурацию на личный сервер, задать секреты в серверном `.env`, запустить `docker compose up -d --build`, проверить UI и три API-эндпоинта по внешнему адресу.
3. Для отката приложения использовать предыдущий образ/коммит и резервную копию БД. Начальная миграция создаёт только новые таблицы; до появления пользовательских данных её можно откатить `alembic downgrade base`.
