# Spec Delta

## Purpose

Контракт API позволяет создать одну проверку набора файлов и затем просмотреть сохранённую историю и полный результат без доступа к содержимому исходных файлов.

## ADDED Requirements

### Requirement: Создание проверки
Система SHALL принимать `POST /api/checks` как `multipart/form-data` с типом записи `daily` или `weekly` и непустым набором файлов. Один запрос SHALL создавать ровно одну проверку, возвращать её готовый результат в JSON и сохранять результат в PostgreSQL.

#### Scenario: Корректный запрос
- **WHEN** передан тип `daily` и хотя бы один файл
- **THEN** сервер возвращает результат проверки с уникальным `check_id`, итоговым `status`, `status_label`, `reason`, `issues`, `documents`, пустым объектом `extracted` и временем `checked_at`

#### Scenario: Пустой набор
- **WHEN** тип записи указан, но файлы не переданы
- **THEN** сервер возвращает HTTP 400 и не создаёт проверку

#### Scenario: Некорректный тип записи
- **WHEN** тип записи отсутствует или отличается от `daily` и `weekly`
- **THEN** сервер возвращает HTTP 422 и не создаёт проверку

### Requirement: Состояние проверки
Система SHALL сначала сохранять запись со статусом `check_in_progress`, затем синхронно обрабатывать файлы, сохранять `complete` или `incomplete` и лишь после этого отвечать на `POST`. Пока обработка идёт, параллельный запрос истории или деталей SHALL иметь возможность увидеть `check_in_progress`.

#### Scenario: Результат POST
- **WHEN** обработка запроса завершилась
- **THEN** `POST /api/checks` возвращает `complete` либо `incomplete`, а сохранённый результат совпадает с ответом

#### Scenario: Промежуточное состояние
- **WHEN** другой запрос читает созданную проверку до завершения обработки
- **THEN** он видит статус `check_in_progress`

### Requirement: История проверок
Система SHALL возвращать по `GET /api/checks` все сохранённые проверки с `id`, датой, типом записи, статусом и количеством материалов. Количество SHALL учитывать каждый загруженный файл, включая непригодные. История SHALL быть доступна после перезапуска приложения.

#### Scenario: Просмотр истории
- **WHEN** сохранены проверки с тремя и четырьмя загруженными файлами
- **THEN** список содержит обе записи с соответствующим количеством материалов и их статусами

### Requirement: Детали проверки
Система SHALL возвращать по `GET /api/checks/{id}` сохранённый полный результат проверки и тип записи. Поля `documents` SHALL содержать каждый загруженный файл с именем, распознанным типом или пустым значением и размером в КБ; исходные байты файлов SHALL отсутствовать в ответе и долговременном хранилище.

#### Scenario: Существующий идентификатор
- **WHEN** клиент запрашивает известный `id` после завершения проверки
- **THEN** сервер возвращает сохранённые статус, замечания, метаданные всех файлов, `extracted: {}` и время проверки

#### Scenario: Неизвестный идентификатор
- **WHEN** клиент запрашивает отсутствующий `id`
- **THEN** сервер возвращает HTTP 404
